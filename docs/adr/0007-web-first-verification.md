# Phase 0 검증 표면은 웹을 우선하고 Slack을 후순위로 미룬다

PRD §9의 「Slack 우선 전달」(채택 가설을 스테이크홀더의 서식지에서 검증) 전달 순서를 뒤집는다. 헤드리스 하네스(Claude Agent SDK, ADR-0005)와 로컬 웹 표면으로 인테이크 → 명확화 루프 → 2층 완결성 판정 → requirements 문서 생성 파이프라인을 먼저 완성·검증하고, Slack 어댑터 운영과 외부 API 사용(Slack·Linear, 직접 API 전환)은 후순위로 미룬다.

근거: Slack 워크스페이스 앱 프로비저닝과 Linear API 토큰이 운영자 의존이라 검증 착수가 막혀 있다(#8 ready-for-human, #10·#11 착수 불가 판정). PoC의 본래 목적 — 프롬프트 품질·파이프라인 검증 — 이 외부 연동 일정에 블로킹되는 것을 해소한다.

구조 결정: 파이프라인 로직은 채널 비의존 코어 러너로 승격하고(원칙 1 — 채널 어댑터), 코어가 회신 게시용 채널 포트를 정의한다. 웹·Slack이 각자 포트를 구현하므로 Slack 복귀 시 어댑터 배선만 남는다. @slack/bolt 경로는 제거하지 않고 봉인한다.

## Trade-off

- **채택 신호(세션 완주율·재사용률)는 Slack 복귀 전까지 미검증.** 웹 표면의 완주율로 중단·전환 기준 (b) 마찰 과다를 부분 판정할 수 있으나, 채택 가설 자체 — 스테이크홀더가 서식지(Slack)에서 실제로 쓰는가 — 는 Slack 복귀 후 재검증이 필요하다.
- 정제 품질 판정(중단·전환 기준 (a))에 필요한 세션 데이터는 웹 PoC에서 동일하게 수집된다 — 세션 영속·버전 귀속·익명화 export는 채널 비의존.

## Considered Options

- Slack 우선 유지(현행): 기각 — 운영자 프로비저닝 완료까지 파이프라인 검증 전체가 대기한다.
- 웹 어댑터 없이 CLI(`pnpm intake`)만으로 검증: 기각 — 다회차 명확화 루프·비동기 재개·문서 열람이 없어 완주율(기준 (b))을 관측할 수 없다.
- 웹 프레임워크 도입: 기각 — 웹 프레임워크 선택은 ARCHITECTURE.md 결정 대기 항목이라 PoC에서 선점하지 않는다. Node 내장 http로 충분하다.

PRD §9 본문 개정은 별도 지시 몫이다 — 이 ADR은 결정 기록만 남긴다.
