## 8. 스코프 제외 (Non-goals)

> **EN** — PRD §8 and §9 — explicit non-goals (no production code, no priority arbitration, no model routing) and the phased plan. Each phase carries kill/pivot criteria as well as pass criteria, on the principle that a plan without a branch for the hypothesis being wrong is not a plan.

- 프로덕션 코드 생성·아키텍처 설계·기술 스택 결정.
- 외부 판매·멀티테넌시·과금·임의 조직 온보딩(내부 도구 확정).
- 목업을 구현 결과물로 납품하거나 하이파이 디자인 제공.
- 완전 자율 이슈 종결(승인 게이트 필수) / 인간 승인 없는 자동 프롬프트·스키마 배포.
- Linear 외 트래커 1차 지원(Jira 등 향후).
- PM 코칭/전략 수립(ChatPRD 영역).
- **모델 라우팅·프로바이더 벤치마크** *(v1.4 추가 — 볼륨상 불필요, §6)*.
- **요청 우선순위 결정·상충 조정의 자동화** *(v1.4 명시)*. 이 제품은 요구를 **정제**하지 결정하지 않는다. 우선순위와 상충 판단은 게이트의 개발자·팀 리드 몫이며, 제품은 판단에 필요한 재료(중복 후보, 과거 결정 이력, 요청자 목록)를 제공하는 데까지다. — *이 경계를 명시하는 이유: "AI PM"이라는 이름이 결정 자동화를 기대하게 만들지만, 결정은 조직 권한의 문제이지 정제 품질의 문제가 아니다.*

## 9. 마일스톤 / 단계별 범위
> 원칙: 채널 비의존은 아키텍처로 지키되, **전달 순서는 가장 위험한 가정(스테이크홀더 채택)부터 검증**한다. 스테이크홀더의 서식지는 Slack이므로 PoC와 첫 전달 표면을 Slack에 둔다.
> *(v1.4)* 각 Phase는 통과 조건뿐 아니라 **중단·전환(kill/pivot) 기준**을 갖는다. 가설이 틀렸을 때의 분기가 없는 계획은 계획이 아니다.

### Phase 0 — PoC + 소급 베이스라인 (1~2주)
- **PoC를 Slack 스레드에서 실행** — 채택 가설과 프롬프트 품질(명확화·문서 생성)을 스테이크홀더의 서식지에서 동시 검증. 하네스: Claude Agent SDK 또는 `claude -p`(F14). Linear는 `issueCreate` 1개 또는 수동. 목업·웹훅·대시보드 범위 외.
- **베이스라인 — 소급 아카이브 분석** *(v1.4 전환)*: v1.3의 "도입 전 1~2주 전향적 기록"을 폐기한다. 대신 최근 6~12개월의 Linear 아카이브에서 개발자의 명확화성 코멘트·reopen·스펙 편집을 추출해 두 가지를 산출한다.
  - (a) **재질문 빈도 베이스라인** — §10 감소율 지표의 분모.
  - (b) **재질문 유형 분류표** — F2e가 필수 슬롯 목록을 도출하는 근거.
  - **전환 근거**: 전향적 2주 기록은 내부 도구 볼륨에서 표본이 10~20건 수준이라 검정력이 없고(문서가 F13 L3에는 검정력을 요구하면서 여기에 요구하지 않는 것은 비대칭이다), Slack PoC와 병행하면 관측 자체가 행동을 바꿔 오염되며, 2주를 대기해야 한다. 소급 분석은 세 문제를 동시에 없애고 표본을 한 자릿수 이상 키운다.
- **산출물**: PoC 리포트 / 프롬프트 v0(레지스트리 등록) / 초기 골든셋 시드 / **재질문 유형 분류표 + 필수 슬롯 초안(F2e)** / 베이스라인 수치.
- **중단·전환 기준** *(v1.4 신설, 수치는 §12)*:
  - **(a) 정제 품질 미달** — 명확화 후 문서의 개발자 검토 통과율이 기준 미만이면 Phase 1을 착수하지 않고, 프롬프트·슬롯을 재설계해 PoC를 재실행한다.
  - **(b) 마찰 과다** — 스테이크홀더 세션 완주율이 기준 미만이면 문제는 정제 품질이 아니라 **마찰**이다. Phase 1의 범위를 "질문 수 축소 + 인테이크 표면 단순화"로 재정의하고, 목업·대시보드를 더 뒤로 민다.
  - **(c) 전제의 부분적 오류** — 소급 분석에서 재질문의 다수가 **요청자 해소 불가 유형**으로 나오면 §2.1의 전제가 부분적으로 틀린 것이다. 이 경우 명확화의 무게중심을 요청자 대화(F2b 축소)에서 컨텍스트 검색·코드베이스 참조(F2a 강화)와 오픈이슈 승격(F2c)으로 옮기고, 제품 서술을 "요청자 명확화 도구"에서 "요청 라우팅·컨텍스트 보강 도구"로 재정의한다. **이 분기는 실패가 아니라 설계 정보다.**

### Phase 1 — MVP (코어 + Slack 어댑터 + 경량 웹 뷰어)
- 채널 비의존 코어: 상태 머신(§7 전체 경로), 세션·신호 스키마, 프롬프트/스키마 레지스트리, 인테이크 API, F2 전체(컨텍스트 그라운딩 + 2층 판정 + **슬롯 3상태·승격 경로**), F3(**원문 보존·슬롯 단위 확인** 포함), F5(**라우팅·SLA·이의 경로** 포함), F6(**provenance** 포함), F8(**중복 병합 + 다중 요청자 최소 모델**).
- **Slack 어댑터를 1차 표면으로**: 인테이크·스레드 명확화·게이트 버튼·역보고 DM.
- **경량 웹 뷰어**: 매직링크로 긴 문서 열람·게이트(Slack의 긴 문서 한계 보완).
- Linear 웹훅 역보고(F7 기본형 + 스펙 변경 판정 규칙).
- **롤아웃 정책 발효**: "모든 기능 요청은 PM Jude 경유" 조직 공지 + **우회 스캐너 가동**(provenance 기반 자동 집계).
- **중단·전환 기준** *(v1.4)*: 정책 발효 +4주 시점에 우회율 또는 중도 이탈율이 기준을 초과하면 **Phase 2(웹 완결 표면·목업)를 착수하지 않고**, 그 리소스를 마찰 감소(질문 수·응답 UX·첫 응답 속도)에 재투자한다. 기능을 더 얹어서 채택 실패를 해결할 수는 없다.

### Phase 2 — 웹 완결 표면 + 목업 + 평가 운영
- 웹 채팅 인테이크·대시보드(F9)·SSO·채널 전환(US-7)으로 웹을 완결 표면화(채널 비의존 원칙의 완성).
- 목업 파이프라인(F4, UI 요청 조건 실행, 호스팅 보안 전체, **역주입 포함**).
- 평가 도구 채택(F12) + 골든셋 v1 + **전수 인간 리뷰 운영(F13 L1)** — "회귀 미통과 배포 불가"를 **코드 강제로** 발효. 판독 큐 점검 항목에 스키마 결손·번역 무결성·역주입 누락 포함.

### Phase 3 — 네이티브화 + 조건부 자동화
- Linear Agents API 파일럿 → 네이티브화(에이전트 시트 비과금으로 비용 장벽 없음; 어댑터 격리 전제로 조기 파일럿 허용, 전면 전환은 GA 후 — 남은 리스크는 Developer Preview 변경뿐).
- 추가 채널(Teams/이메일).
- **F13 L2**(judge 보조·자동 분류)는 §12 임계치 충족 시에만.
- **build-vs-buy 재결정 게이트** *(v1.4 신설)*: 이 시점에 §2.5의 재결정 조건을 정식 평가한다. 트래커 벤더가 다회차 명확화 루프와 완결성 게이트를 GA로 제공하면, F2·F3의 자체 유지 여부를 재질문 유형 분류표 커버리지 기준으로 판단한다. 폐기가 정답이면 폐기한다.

### Phase 3+ (옵션)
- F13 L3(A/B·자동 개선 제안) — 통계적 검정력 확보 시에만. 내부 도구 볼륨에서 도달하지 않으면 도입하지 않는다.
