## 5. 기능 요구사항 (F1–F14)

> **EN** — PRD §5 — functional requirements F1 through F14, grouped into core (channel-agnostic), channel adapters, evaluation and improvement, and the PoC harness. The load-bearing ones are F2 (clarification engine: context grounding, targeted questions, two-layer completeness check, slot tri-state), F5 (gate routing and SLA), F8 (terminal states) and F12 (deployment gate).

기능은 **코어(채널 무관)**, **채널 어댑터**, **평가·개선**, **PoC 하네스**로 구분한다.

### F1 — 인테이크 (코어 + 웹 + Slack 어댑터)
- **F1-Core**: 채널 무관 수신, 통합 프로필·세션 생성, 즉시 확인 응답. 프로필에 **선호 언어·시간대** 저장. 세션은 **요청자 ≠ 실사용자**(대리 요청)와 **N명의 요청자**를 표현할 수 있는 스키마를 갖는다 *(v1.4 — 중복 병합의 전제)*.
- **F1-Web**: 웹 채팅 인테이크, 매직 링크/SSO.
- **F1-Slack**: 멘션/DM/이모지 인테이크. Bolt for TypeScript + Assistant 스레드, 스레드 컨텍스트 스토어.
- **F1-Attach — 자료 첨부** *(v1.5 신설)*: 요청자는 **발화에 자료를 첨부**할 수 있다. 붙일 수 있는 지점은 요청자가 입력을 넣는 모든 곳이다 — 인테이크, 명확화 답변, 보류 재개 입력, 슬롯 정정. 첨부는 별도 채널이 아니라 **명확화 입력**이며, 추출 텍스트가 질문 생성(F2b)과 완결성 판정(F2c)에 실린다. 지원 타입은 MIME별 **추출기 레지스트리**로 관리하고 미등록 타입은 명시적으로 거부한다(무음 통과 없음). 모델에 닿는 경로는 텍스트 하나이며 이미지는 등록된 추출 프롬프트로 서술 텍스트가 된다. 원본은 불변 보존하고 추출 텍스트는 추출기 버전을 단 재생성 가능한 캐시다. 세션당 추출 텍스트 총량 상한을 두고 초과분은 업로드 시점에 거부한다 — 요약 압축이나 무음 절단으로 우회하지 않는다. 결정 근거는 [ADR-0011](../adr/0011-attachment-as-clarification-input.md).
- **수용기준**: 두 채널 모두 접수 3초 이내 확인 / 동일 코어 세션 스키마 / 처리 상태 표시 / 요청자 목록이 1명 이상 N명까지 확장 가능 / **첨부가 접수 확인을 지연시키지 않음(추출은 접수 응답 뒤 백그라운드)** / **미지원 타입·상한 초과가 업로드 시점에 사유와 함께 거부됨** / **추출 실패가 세션을 멈추지 않고 무엇을 읽지 못했는지 요청자에게 고지됨**.

### F2 — 명확화 엔진 (코어)

**(a) 컨텍스트 그라운딩** — 질문 생성 *전에* 기존 자료를 검색해 요청을 맥락화한다. 검색 대상 *(v1.4 확장)*:
  1. 기존 Linear 이슈, 2. 과거 `requirements` 문서, 3. 등록된 제품 문서, **4. 종결된 과거 세션과 게이트 결정 이력(거절·백로그 사유 포함)**.
  4번이 v1.4의 추가분이다. 데이터는 F5/F11이 이미 수집하고 있으므로 추가 비용이 거의 없고, **조직 기억**이 여기서 생긴다 — "이 요청은 3월에 X 사유로 거절되었습니다"를 명확화 시작 시점에 즉시 회신할 수 있다.
  이 검색은 시스템에서 유일하게 LLM에게 자율성이 허용되는 **경계 지어진 툴콜 루프**다(검색 도구만 노출, 호출 횟수 상한). 효과: 이미 답이 있는 것을 묻지 않고, generic 질문을 방지하며, **유사 기존 요청을 중복 후보로 제시**한다.

**(b) 표적 질문 생성** — ClarifyGPT식: 동일 요청의 그럴듯한 해석 후보를 다중 전개하고, 해석이 갈라지는 지점(누가 쓰나, 어떤 질문에 답하나, 데이터는 어디서, 얼마나 자주)을 표적 질문으로 전환. 한 번에 3~5문항, 요청자의 언어로, 비즈니스 어휘로, 예시 선택지 제공. **각 질문에는 "모르겠다 / 개발팀이 정할 문제다" 응답 경로가 항상 함께 제시된다** *(v1.4 — US-10)*.

**(c) 2층 완결성 판정** *(v1.4 — 슬롯 3상태화)*

- **슬롯의 3상태**: 각 필수 슬롯은 `충족` / `미충족` / **`승격(요청자 해소 불가)`** 중 하나다. 세 번째가 v1.4 신설이다. 요청자가 원리적으로 답할 수 없는 항목(어느 테이블이 진실 원천인가, 기존 권한 모델을 따르는가, 과거 데이터 처리 방침 등)은 **담당자가 지정된 오픈이슈로 승격**되어 문서의 `오픈이슈` 필드에 실린다. 승격은 요청자의 1클릭(US-10) 또는 LLM 층의 판정으로 트리거된다.
- **룰 층(결정론적 백스톱)**: 통과 조건은 **"모든 필수 슬롯이 `충족` 또는 `승격`"**이다. `미충족`이 하나라도 남으면 LLM 점수와 무관하게 미정제 — 예: "대시보드 만들어줘"는 전 슬롯 `미충족`이므로 즉시 미정제. 추가 형식 검사: 모든 스토리에 Given/When/Then 존재, 수용기준 내 금칙 모호어("적당히", "빨리", "개선" 등 사전 정의 목록) 부재, EARS 구문 충족.
- **왕복 상한 도달 시의 강제 판정** *(v1.4 신설 — v1.3의 데드락 해소)*: v1.3에서는 "왕복 상한 존재 + 룰 미통과 시 게이트 진입 불가 + 침묵 금지"가 동시에 성립해, 상한에 도달했는데 슬롯이 빈 요청은 **진행도 종결도 불가능**했다. v1.4의 처리:
  1. 남은 `미충족` 슬롯 각각에 대해 **승격 가능 여부를 판정**한다.
  2. 승격 가능하면 오픈이슈로 올리고 **"조건부"로 게이트에 상정**한다. 게이트 UI는 이 상태를 시각적으로 구분한다(US-5).
  3. 승격도 불가하면(요청 자체가 무엇을 원하는지 판별 불가) 게이트에 상정하지 않고, 사유를 담은 회신 후 **`보류(정보 부족)`로 종결**한다. 요청자는 언제든 재개할 수 있다.
  - **어느 경우에도 세션이 멈춘 채 방치되지 않는다**(원칙 5).
- **LLM 층(의미 판정)**: 슬롯이 채워진 뒤에도 남은 의미적 모호성을 해석 발산 재검사와 루브릭 점수로 판정. LLM이 정제를 수행하고, 룰은 LLM의 알려진 약점(과신에 의한 조기 통과)을 막는 안전핀이다.
- **슬롯 근거의 출처** *(v1.5 신설)*: 슬롯을 `충족`으로 만드는 근거는 요청자 발화 또는 **첨부 자료**(F1-Attach)다. 첨부에서 판정된 값은 **어느 첨부에서 왔는지 세션에 기록**하고, 요청자 확인 시 출처를 함께 표시한다(F3). 추출과 해석을 거친 값은 요청자가 말한 적 없는 값이므로, 출처 없이 제시하면 「맞아요 / 아니에요」가 판단 가능한 물음이 되지 않는다. 이 기록은 F13 판독에서 **추출 결함과 프롬프트 결함을 가르는 근거**이기도 하다 — 프롬프트 결함과 스키마 결손의 구분(F2e)과 같은 종류의 분기다.

**(d) 다국어** — 대화는 요청자 언어, 산출 문서는 팀 표준 언어. **원문 전사는 상시 보존**(옵션 아님, 원칙 7).

**(e) 슬롯 목록의 근거 관리** *(v1.4 신설)* — 필수 슬롯 목록은 일반 요구공학 문헌이 아니라 **이 조직의 실측 재질문 데이터**에서 도출한다.
  - 최초 목록 *(v1.6 개정, [ADR-0012](../adr/0012-prospective-self-measurement.md))*: **개발자 엘리시테이션 시드**(요청 수신 시 실제로 되묻는 항목 수집)에서 파생하고, 슬롯마다 근거(derivedFrom)를 기록한다. v1.4의 소급 분류표 경로는 폐기 — 요청자↔개발자 명확화 대화가 아카이브에 없다.
  - 갱신: F11의 재질문·reopen 신호로 분기 점검한다.
  - **판정 규칙**: 어떤 재질문 유형이 반복 발생하는데 대응 슬롯이 없다면 그것은 프롬프트 문제가 아니라 **스키마 결손**이며, F13의 개선 후보에 "룰 목록 보강"으로 올린다. 슬롯이 다 찬 문서가 여전히 재질문을 유발하는 상황에서 프롬프트만 손보는 것이 이 시스템의 가장 그럴듯한 실패 모드이므로, 이 구분을 제도화한다.
  - **수용기준**: 각 필수 슬롯이 최소 1개의 근거(엘리시테이션 항목 또는 런타임 재질문 유형)에 매핑되어 출처를 남김 / 근거 없는 슬롯은 추가하지 않음 / 미매핑 재질문 유형이 US-9 대시보드에 노출.

**F2 전체 수용기준**: 각 질문이 특정 모호성 또는 공백 슬롯에 매핑 / 검색 결과가 세션에 기록(무엇을 참조했는지 추적 가능) / 룰·LLM 판정과 슬롯 3상태가 각각 세션에 기록 / 전 과정이 F11 신호 스키마로 로깅 / 왕복 상한 존재(수치는 §12) / 상한 도달 시 위 3분기 중 하나로 반드시 귀결.

### F3 — 요구사항 문서 생성 (코어)
- `requirements`(문제 / 사용자 / 스코프 / 유저스토리+수용기준(Given-When-Then, EARS) / 데이터 소스 / **오픈이슈(승격 슬롯 + 담당자)**) + `tasks` 분해. "어떻게"는 비운다.
- **번역 무결성** *(v1.4 신설 — 원칙 7)*: 문서는 팀 표준 언어로 산출하되,
  - **원문 전사를 상시 보존**하고 이슈에 첨부한다(옵션 아님).
  - **요청자 확인은 산문 번역본이 아니라 구조화 슬롯 값 단위로, 요청자 언어로** 제시한다. 산문의 왕복 번역은 오류를 감추지만, 슬롯 단위 확인("대상 사용자: 영업팀 매니저 — 맞습니까?")은 오류를 드러낸다.
  - 요청자도 개발자도 검증할 수 없는 번역 구간을 남기지 않는다. 판독 큐(F13)는 표본 대조를 점검 항목으로 갖는다.
- **첨부 유래 확정 사항의 흡수** *(v1.5 신설 — 원칙 7)*: 첨부 자료(F1-Attach)에서 확정된 것은 `requirements` vN의 **문장으로 흡수**하고, 첨부 파일 자체는 원문 전사와 같은 지위로 「참고용 — 구현 근거는 문서」 표기와 함께 동봉한다. **첨부를 지워도 문서만으로 구현 가능한 상태**가 목표이며, 이는 F4가 목업 역주입에 요구하는 규율과 같다. 슬롯 확인 화면은 첨부 유래 값에 출처를 표시한다(F2c).
- **수용기준**: 아키텍처·코드·스택 미포함 / 각 스토리에 검증 가능한 EARS 수용기준 / 문서 vN이 세션·프롬프트 버전에 귀속 / 원문 전사 첨부 / 요청자 확인이 슬롯 단위·요청자 언어로 수행된 기록 존재 / **첨부 유래 확정 사항의 문서 반영 누락 0** / **첨부 유래 슬롯 값에 출처 표시**.

### F4 — 목업 생성·호스팅·피드백 (코어, **조건 실행**)
- **전제 조건**: 명확화 종료 시 요청을 분류한다 — **UI 변화를 수반하는가?** 비 UI 요청(데이터 수정, 리포트/배치, 성능, 인프라 등)은 목업 단계를 **생략**하고 F3의 슬롯 단위 문서 검증으로 대체한다.
- UI 요청: 자체 LLM이 단일 self-contained **인터랙티브 HTML** 목업 생성(중간충실도, 그레이스케일, 더미데이터, "요구사항 확인용 목업 — 구현 결과 아님" 워터마크). 호스팅된 URL을 채팅에 전달.
- **호스팅·보안**: 앱 도메인과 분리된 샌드박스 usercontent 도메인(Cloudflare R2 + Workers 권장), 만료 서명 URL, CSP `sandbox` + `default-src 'none'` + 외부 네트워크 차단, 뷰어 iframe `sandbox="allow-scripts"`(allow-same-origin 배제), postMessage origin 검증, Slack 전송 시 `unfurl_links:false`/`unfurl_media:false`.
- **버전 매핑**: 요구사항 vN ↔ 목업 vN ↔ URL vN. 최대 2~3회 반복 후 수렴 또는 에스컬레이션.
- **역주입(문서 흡수)** *(v1.4 신설 — 원칙 7)*: 목업 승인 시, 반복 과정의 어노테이션·코멘트에서 **확정된 요구사항을 `requirements` vN+1의 문장으로 흡수**한다(예: "목업 v2에서 확정 — 필터 3종(기간·팀·상태), 기본 기간 30일, 빈 상태 문구 표시"). 2~3회 반복하면 목업에만 존재하고 문서에는 없는 확정 사항이 반드시 생기는데, F6은 목업을 "구현 기준 아님"으로 보내므로 그 정보는 공식적으로 아무 데도 없게 된다. 역주입은 이 누수를 막는다.
  - 흡수 후 **목업은 폐기 가능해야 한다** — 목업을 지워도 문서만으로 구현 가능한 상태가 목표다.
  - 게이트는 흡수 완료 여부를 표시하고, 판독 큐는 어노테이션 대비 문서 반영 누락을 점검 항목으로 갖는다.
- **수용기준**: 비 UI 요청에서 목업 미실행 / UI 요청에서 조작 가능 URL 전달 / 워터마크 상시 / 반복·어노테이션이 F11 신호로 기록 / **목업 반복 종료 시 어노테이션 대비 문서 반영 누락 0**.

### F5 — 개발자 승인 게이트 (코어)
- 승인/질문/백로그/거절 4버튼, **비동기 동작**. **승인 시에만** Linear 이슈 생성 — 이 제약은 상태 머신 코드로 강제(원칙 2).
- **라우팅** *(v1.4 신설)*: 게이트 수신자는 (1) 요청이 매핑된 Linear 팀/영역의 담당자, (2) 미매핑 시 팀 기본 승인자(F10 설정), (3) 부재(휴가·상태) 시 대체자 순으로 결정한다. **라우팅 근거를 세션에 기록하고 게이트 UI에 표시**한다("이 요청이 당신에게 온 이유: 대시보드 영역 담당"). PM 없는 팀에서 "이 요청은 누구 것인가"는 사소한 문제가 아니며, 이 제품은 모든 요청을 게이트로 모으므로 **새 병목을 하나 만든다**는 사실을 설계에 반영한다.
- **SLA와 미응답 처리** *(v1.4 신설)*: 게이트 항목은 SLA(F10 설정, 수신자 근무시간 기준)를 갖는다. 1차 리마인더 → 2차 리마인더 + 대체자 병행 통보 → **SLA 초과 시 자동 백로그 전환 + 요청자 회신**. 게이트가 무기한 대기 상태로 남는 경로는 존재하지 않는다(원칙 5의 양방향 적용).
- **거절 사유와 이의 경로** *(v1.4 신설)*: 거절은 **통제된 사유 목록**(우선순위 / 스코프 밖 / 중복 / 기술적 불가 / 정보 부족)에서 선택한다. 회신에는 **이의 경로(팀 리드 재검토 요청)**를 명시한다. 개발자가 조직 서열이 높은 요청자를 거절하는 상황은 실재하며, 이의 경로가 제품 안에 없으면 그 갈등은 제품 밖의 우회로 해소된다.
- **조건부 상정** *(v1.4)*: 오픈이슈로 승격된 슬롯이 있는 건은 시각적으로 구분 표시되고, 게이트 결정 시 오픈이슈의 담당자 지정이 함께 확정된다.
- **수용기준**: 승인 없이 이슈 미생성 / 모든 결정과 라우팅 근거 기록 / 반려·질문 시 사유 태그 1클릭(F11 귀속) / SLA 초과 건이 0으로 수렴(대기 상태 잔존 없음) / 질문·백로그·거절·보류 시 F8 회신 트리거.

### F6 — Linear 연동: 이슈 생성 (코어 커넥터)
- GraphQL `issueCreate`(@linear/sdk). 본문에 스펙 + **원문 전사 첨부** + 목업 링크("참고용, 구현 기준 아님" 라벨) + 오픈이슈(담당자 지정) 섹션.
- **세션 귀속(provenance)** *(v1.4 신설)*: 생성된 모든 이슈에 세션 ID를 **기계 판독 가능한 형태**(커스텀 필드 또는 규약된 라벨)로 남긴다. 이것이 §10 우회율 자동 집계의 전제다 — 귀속 없는 기능 요청 이슈 = 우회 후보.
- **중복 병합 처리** *(v1.4)*: 병합 세션은 새 이슈를 만들지 않고 기존 이슈에 요청자를 구독자로 추가하고 요청 맥락을 코멘트로 첨부한다.
- **수용기준**: 승인 즉시 생성 / 라벨링 / 실패 시 재시도·오류 알림 / 이슈 ID 세션 귀속 / **모든 생성 이슈에 세션 provenance 존재**.

### F7 — 진행도 추적·역보고 (코어 + 채널 알림)
- Linear 웹훅 기반(폴링 지양), Issue/Comment 구독, `Linear-Signature` HMAC-SHA256 + `webhookTimestamp` 1분 검증 + `webhookId` 중복 제거, 10초 이내 응답(비동기 처리).
- 알림: Slack 연동 시 DM, 미연동 시 웹/이메일. 수신자 시간대 인지. **요청자가 N명이면 각자의 언어·시간대로 팬아웃** *(v1.4)*.
- **"스펙 변경" 신호의 판정 규칙** *(v1.4 신설)*: 이슈 본문의 임의 편집을 신호로 삼지 않는다 — 서식·오탈자 수정이 섞여 노이즈가 된다. PM Jude가 생성한 **구조화 섹션(스코프 / 수용기준 / 데이터 소스)의 의미 변경**만 카운트하며, 판정은 **섹션 단위 diff → LLM 의미 변경 여부 확인**의 2단계로 수행한다. 판정 결과는 세션에 근거와 함께 기록한다.
- **수용기준**: 서명 실패 4xx / 상태 변경의 채널별 전달 / 이슈 라이프사이클 신호(재질문·reopen·스펙 변경·취소)가 위 규칙에 따라 F11로 추출·귀속.

### F8 — 종결 상태와 회신 UX (코어) *(v1.4 확장)*
- **종결 상태 목록** *(v1.4 갱신)*: `이슈 생성(승인)` / **`중복 병합`** / `백로그` / `거절` / **`보류(정보 부족)`**. 모든 종결 상태는 회신을 트리거한다.
- **중복 병합** *(v1.4 신설)*: F2a가 제시한 중복 후보를 요청자가 수락하면 새 이슈 없이 기존 이슈에 연결한다. 요청자는 구독자로 등록되어 **F7 역보고를 그대로 수신**하고, 요청 원문·맥락은 기존 이슈에 코멘트로 첨부되어 소실되지 않는다. 인테이크에서 ROI가 가장 높은 기능이므로 절반만 구현하지 않는다.
- **다중 요청자** *(v1.4 — Phase 1 필수로 승격)*: 병합이 동작하는 순간 1이슈 N요청자가 즉시 발생한다. 따라서 Phase 1은 **최소 모델**(요청자 목록 보유 + 역보고 팬아웃 + 각자 언어·시간대 적용)을 반드시 포함한다. 상충 해소 절차의 정식 모델은 §12.
- **거절/백로그**: 통제된 사유 목록 기반의 정중한 회신(요청자 언어) + **이의 경로 안내**. **백로그 재부상**: 유사 요청 누적(중복 후보 매칭 N회) 또는 정기 리뷰 주기 도래 시 게이트에 재상정하고 요청자에게 안내(트리거 수치는 §12).
- **수용기준**: 5개 종결 상태 모두가 회신 트리거 / 사유 필수 / 병합 시 구독 등록과 원문 첨부 확인 / 재부상 이벤트 기록.

### F9 — 요청 대시보드 (웹)
- 요청 목록/상태/진행도. 스테이크홀더/개발자/관리자 뷰. 개발자용 승인 대기 큐(SLA 잔여 표시), 관리자용 파이프라인·품질 지표.
- **v1.4 추가 뷰**: 판독 큐(전수 리뷰), **우회 후보 큐**(provenance 없는 기능 요청 이슈), **재질문 유형 ↔ 슬롯 매핑 현황**(미매핑 = 스키마 결손 후보).
- **수용기준**: 세션별 채널·상태·리드타임 표시 / 시간대별 표기 현지화 / 게이트 대기 시간이 리드타임과 분리 표시.

### F10 — 관리 설정 (웹)
- 승인 권한, **게이트 라우팅 규칙·SLA·근무시간 정의** *(v1.4)*, **거절 사유 목록 관리** *(v1.4)*, 채널 연결(Slack on/off), 비용 상한, 팀 표준 문서 언어, 백로그 재부상 규칙, 평가·개선 설정(리뷰 담당, 배포 승인자), **롤아웃 정책 텍스트 관리**("모든 기능 요청은 PM Jude 경유" 공지문), **우회 집계 필터 정의**(어떤 이슈 타입/라벨을 "기능 요청"으로 볼 것인가) *(v1.4)*.
- **수용기준**: admin 전용 / 비용 상한 가드레일 / 채널 해제 시 자동 폴백 / SLA·라우팅 변경이 즉시 반영.

### F11 — 품질 신호 수집·귀속 (평가·개선)
정제 품질의 궁극 판정자인 **다운스트림 실측 신호**를 수집하고, 각 신호를 세션과 당시의 프롬프트/모델/임계치/**슬롯 스키마** 버전에 귀속한다 *(v1.4 — 스키마 버전 추가)*.

| 신호 | 출처 | 의미 |
|---|---|---|
| 승인 게이트 결정 + 사유 태그 | F5 버튼 | 1차 품질 판정(반려/질문율 = 정제 실패의 선행 지표) |
| 게이트 대기 시간·SLA 초과 *(v1.4)* | F5 | 게이트 병목의 조기 경보 |
| 이슈 재질문 코멘트 | F7 웹훅 — 개발자가 "스펙 불충분" 1액션 표시 | 승인 통과 후 드러난 정제 결함. **유형 분류가 F2e 슬롯 갱신의 입력** |
| 이슈 reopen·스펙 변경·취소 | F7 웹훅(스펙 변경은 §F7 판정 규칙 적용) | 구현 단계에서 드러난 요구사항 오류 |
| 목업 반복 횟수·어노테이션 밀도 | F4 | 명확화가 시각화 전에 수렴 못 한 정도 |

| 명확화 왕복 수·완결성 점수·**슬롯 승격 건수** *(v1.4)* | F2 로그 | 대화 품질 / 요청자 해소 불가 비율(§2.1 전제 검증) |

| **첨부 추출 실패·첨부 유래 슬롯 정정** *(v1.5 신설)* | F1-Attach 추출 결과 / F3 슬롯 확인 | 추출 품질. 정정률이 발화 유래보다 유의하게 높으면 프롬프트가 아니라 **추출기**를 고친다 |

### F12 — 평가 하네스: 구축이 아니라 채택
프롬프트·스키마·임계치 변경을 안전하게 만들기 위한 평가 기반. **범용 인프라(트레이싱, 프롬프트 버전 관리, 평가 실행, 대시보드)는 자체 구축하지 않고 기존 도구를 채택한다** — 후보: Langfuse(오픈소스, 셀프호스트), promptfoo(회귀 평가 러너). 자체 구축 범위는 도메인 특화 부분으로 한정: F11 신호 귀속 스키마, 골든셋 큐레이션 절차, 배포 게이트 연동.
- **골든 데이터셋**: 익명화된 실제 세션에서 큐레이션(PoC 세션이 시드). 성공·실패 사례 포함, 평가용/개선용 분리, 분기 갱신, 골든셋 자체도 버전 관리.
- **배포 게이트는 프로세스가 아니라 통제다** *(v1.4 시정)*: v1.3의 "회귀 미통과 변경의 배포 불가"는 프롬프트가 평가 도구 UI에서 편집 가능한 이상 **프로세스에 불과**했다. 원칙 2("하드 제약은 코드로 강제")를 여기에도 적용한다 — **런타임 게이트웨이는 `회귀 통과` 플래그가 붙은 프롬프트/스키마 버전만 로드**하며, 플래그 없는 버전은 도구 UI에서 저장되더라도 프로덕션 세션에 사용될 수 없다.
- **프롬프트 레지스트리**: 채택 도구의 버전 관리 기능 사용. 런타임 세션은 항상 명시적 버전 참조(F11 귀속의 전제).
- **LLM-as-judge는 기본 비활성**: 도입 조건(§12 임계치) 충족 전까지 회귀 평가의 채점은 룰 검사 + 운영자 판독으로 수행.
- **수용기준**: 플래그 없는 버전의 런타임 로드가 코드 수준에서 불가 / 평가 실행 재현 가능 / 채택 도구가 셀프호스트 또는 사내 데이터 정책 충족.

### F13 — 개선 루프 운영: 볼륨에 맞는 자동화
신호 → 진단 → 개선 → 검증 → 배포 → 재측정의 닫힌 사이클. **자동화 수준은 요청량에 따라 단계 도입한다.**

```
[F11 신호 수집]
      ↓
[전수 인간 리뷰] — 운영자가 모든 세션 판독(저볼륨 1차 수단)
   실패 유형 분류: 질문 미스타겟 / 완결성 과대평가 / 목업 오해 유발 /
   문서 구조 결함 / 언어 부적합 / 스코프 판단 오류 /
   [v1.4 추가] 스키마 결손(슬롯 없음) / 번역 무결성 위반 / 목업 역주입 누락 /
   [v1.5 추가] 추출 결함(첨부를 잘못 읽음 — 프롬프트 결함과 구분)
   ※ 판독 기록 = 미래 LLM-judge 보정용 라벨 자산
      ↓
[개선 후보 분기] — (a) 프롬프트 수정·few-shot 추가·임계치 조정
                  (b) [v1.4] 슬롯 스키마 보강 ← 재질문 유형에 대응 슬롯이 없을 때
      ↓
[인간 승인 게이트] — 운영자 검토·승인(자동 배포 금지)
      ↓
[오프라인 회귀 평가] — F12 골든셋 통과 필수(코드 강제 배포 게이트)
      ↓
[카나리 배포] — 신규 세션 일부에 새 버전(볼륨 무관 유지되는 안전장치)
      ↓
[재측정 리포트] — 버전별 F11 신호 비교 → 승격/롤백
      ↺
```

- **개선 후보 분기가 v1.4의 핵심 추가다.** 슬롯이 다 찬 "완결" 문서가 여전히 재질문을 유발하는데 프롬프트만 반복 수정하는 것이 이 시스템의 가장 그럴듯한 헛돌기다. 판독 시 **"이 재질문에 대응하는 슬롯이 있는가"**를 먼저 묻고, 없으면 프롬프트가 아니라 스키마를 고친다.
- **자동화 단계와 도입 조건**: **L1** 전수 인간 리뷰 + 수동 개선(Phase 2 기본) → **L2** LLM-judge 보조 채점 + 실패 자동 분류(도입 조건: 주간 세션 수·축적 라벨 수 임계치 충족, judge-인간 일치율 검증 통과) → **L3** A/B 실험·자동 개선 제안(도입 조건: 통계적 검정력이 확보되는 트래픽 — 내부 도구에서는 도달하지 않을 수 있으며, 도달하지 않으면 도입하지 않는다). 어느 단계에서도 인간 승인 게이트는 유지.
- **수용기준**: 전 세션이 판독 큐에 적재되고 판독 기록이 라벨로 저장 / 실패 유형이 프롬프트 결함과 스키마 결손으로 구분 분류 / 모든 개선 배포에 카나리와 재측정 리포트 / 승격·롤백 기록 / 자동 제안은 예외 없이 인간 승인 경유.

### F14 — PoC LLM 하네스: Claude Code 헤드리스 (*Phase 0 한정*)
PoC에서는 프로바이더 API 직접 구성 대신 **Claude Code 헤드리스 하네스**를 게이트웨이의 첫 백엔드로 사용한다 — CLI `claude -p` 또는 **Claude Agent SDK**(세션·구조화 출력·툴 권한 제어를 SDK가 처리하므로 권장). 목적: 인프라 최소화, **명확화·문서 생성 프롬프트 품질의 조기 검증**.
- **호출 규약**: 게이트웨이 표준 인터페이스(`complete(promptVersion, input) → structuredOutput`) 뒤에 격리. CLI 사용 시 `--output-format json` 파싱·스키마 검증. 프롬프트 본문은 반드시 레지스트리 버전 참조 — PoC 세션도 F11 귀속 대상.
- **안전 규약**: 파일시스템·셸 도구 비활성화(F2a 검색 도구만 예외적으로 허용 가능), 서버 측 격리 실행, 사용자 입력을 셸 인자로 보간하지 않음(stdin/임시 파일).
- **운영 규약**: 타임아웃·동시 실행 상한, 비용/사용량 로깅. 세션 컨텍스트는 자체 저장소에서 조립해 **무상태 호출**로 주입.
- **전환(Exit) 기준**: PoC 목표 달성 시 직접 API로 교체, 하네스는 폐기 또는 로컬 개발 전용 격하. 전환 전후 골든셋 시드로 출력 동등성 확인 + 타 프로바이더 교차 평가(단일 모델 고착 방지).
- **수용기준**: 하네스 호출이 게이트웨이 외부로 누출되지 않음 / PoC 세션도 버전 귀속 / 도구 제한 상태로만 실행 / 전환 시 코드 변경이 게이트웨이 구현체 1곳으로 한정.
